Phase 3 adds explicit caller-supplied font registration. Pass a `FontConfiguration` when creating the engine; the exact face metadata, aliases, fallback family, and immutable font bytes become compatibility inputs. When no font configuration is supplied, the historical built-in Helvetica/WinAnsi fallback remains available.

## Reference playground policy

The reference playground intentionally exposes a narrower policy than the low-level library API:

- available font programs must come from an application-owned, version-pinned static TrueType catalog;
- uploaded DOCX embedded-font programs are not registered or executed;
- familiar system family names are deterministic aliases to catalog faces, never operating-system font lookups;
- an unavailable family remains explicit in diagnostics until it is added to the pinned catalog;
- rendering never discovers an OS font or fetches one from a third-party runtime service.

The browser catalog self-hosts five OFL-1.1 families: Inter, Bricolage Grotesque, Instrument Sans, Instrument Serif, and Geist Mono. Every TTF and its SHA-256 digest is recorded in `@apex-docx-pdf/fonts`; the playground worker registers those exact bytes and the UI specimens use the same assets. `Arial`, `Calibri`, and `Helvetica` alias to Inter; `Times New Roman` aliases to Instrument Serif; and `Courier New` aliases to Geist Mono. Compact PostScript-style names such as `InstrumentSans` and `GeistMono` also map to their canonical family names. Common DOCX family labels that include a weight suffix select a pinned static face: `Inter Medium` and `Bricolage Grotesque Medium` select 500, while their `SemiBold` forms select 600.

Inter provides 400, 500, 600, and 700 normal faces plus 400 and 700 italics. Bricolage Grotesque provides 400, 500, 600, and 700 normal faces. Instrument Sans and Geist Mono provide 400 and 700 in normal and italic styles, while Instrument Serif provides 400 normal and italic. Requests for missing combinations use deterministic nearest-weight fallback; the playground does not synthesize or mislabel extra font programs. The visible specimens enumerate each bundled normal weight. Vite emits these files with the self-hosted app, so local asset requests remain offline-capable and never contact font CDNs.

Variable-font axis selection is not implemented. Register one static, named font program for every weight/style tuple you promise. Registering the same variable-font bytes under several weights does not instantiate different outlines and is not treated as weight support. The legacy `Inter Variable` family alias only maps the family into this static catalog; it does not activate a variable axis.

## Configure font bytes explicitly

```ts
const fonts = {
  faces: [
    {
      family: "Example Sans",
      weight: 400,
      style: "normal",
      bytes: exampleSansBytes,
    },
  ],
  fallbackFamily: "Example Sans",
} as const

const engine = await createDocxPdfEngine({ fonts })
```

The fallback family must contain a 400 normal face. Faces accept the CSS/OpenType static weights 100 through 900 in increments of 100 and styles `normal` and `italic`. Optional aliases resolve to registered families and may select a specific weight or style when the source family name encodes it. The engine snapshots supplied `Uint8Array` values and the font registry exposes a deterministic hash.

No part of this path discovers system fonts, reads font files, fetches a font URL, or depends on Node.js `Buffer`. The application owns acquisition of the bytes and must have the right to embed and distribute them.

## Deterministic matching

Within a requested or aliased family, matching first prefers the requested style and then applies CSS nearest-weight ordering. A 400 request checks 500 before lighter weights and then 600–900; a 500 request checks 400 before lighter weights and then 600–900; lighter requests search downward then upward; heavier requests search upward then downward. An unavailable italic then repeats the weight search with normal style. If the family has no match, the same sequence is applied to the configured fallback family.

## Shaping and embedding

Exact-pinned `fontkit` 2.0.4 parses font metrics and shapes well-formed left-to-right Latin text. Complex scripts, right-to-left text, and bidirectional layout are outside the current boundary.

For TrueType, the PDF serializer emits a Type0 font with a CIDFontType2 descendant, FontDescriptor, FontFile2 stream, CIDToGIDMap, and ToUnicode CMap. Each shaped glyph receives an absolute PDF position, preserving fontkit advances and offsets while keeping text searchable.

By default, the registry embeds the complete immutable TrueType program and returns `subsetted: false`. There is an injectable deterministic subsetting seam with an explicit source-to-subset glyph mapping, but the repository does not provide true font subsetting today. OpenType/CFF is diagnosed as unsupported for PDF embedding.

## Historical fallback

Without `FontConfiguration`, the Phase 1 path still measures and serializes built-in Helvetica with WinAnsi encoding. Non-Helvetica family and style requests produce compatibility warnings. Characters outside WinAnsi produce an error, and the high-level engine returns no render result rather than exposing an incomplete PDF.

Read [ADR 0004](/adr/0004-fontkit-full-font-embedding) for the dependency, licensing, determinism, and full-embedding decision.
