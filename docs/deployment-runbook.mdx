---
title: "Deployment runbook"
description: "Approval-gated Vercel and Mintlify deployment, smoke, promotion, and rollback steps."
---

This runbook separates locally verified preparation from actions that change a Vercel, Convex, Mintlify, DNS, or npm environment. Do not run a command in an **external action** section without narrow action-time approval for that exact environment.

## 1. Local release gate

Run from the repository root without production credentials:

```bash
bun install --frozen-lockfile
bun run ci
git status --short
```

`bun run ci` includes formatting, Biome linting, TypeScript checks, the Bun test suite, the explicit seeded property/fuzz gate, exact Bun/Node/Chromium render parity, the real-application Chromium playground and automated axe smoke, Mintlify validation, release-configuration validation, the production build, and package validation. Review the worktree after the gate; a green build does not authorize deployment or publication.

## 2. Required configuration

The web build reads these public values:

| Variable                     | Required for                   | Value                                                                      |
| ---------------------------- | ------------------------------ | -------------------------------------------------------------------------- |
| `VITE_CONVEX_URL`            | Opt-in persistence             | The deployed Convex client URL. Omit it to keep the playground local-only. |
| `VITE_DOCS_URL`              | Canonical documentation links  | The deployed Mintlify site origin, without a trailing slash.               |
| `VITE_SITE_URL`              | Canonical application origin   | The deployed web origin, without a trailing slash.                         |
| `VITE_CLERK_PUBLISHABLE_KEY` | Signed-in `/app` and `/editor` | Clerk publishable key (`pk_test_…` or `pk_live_…`).                        |

The server runtime also requires this secret. Never place it in a `VITE_*` variable or ship it to the browser:

| Variable           | Required for                      | Value                                          |
| ------------------ | --------------------------------- | ---------------------------------------------- |
| `CLERK_SECRET_KEY` | Clerk middleware and route guards | Clerk secret key (`sk_test_…` or `sk_live_…`). |

Clerk Dashboard must allow each deployed origin and the OAuth callback:

- allowed origins: `http://localhost:3000`, the production site origin, verified aliases, and Preview deployment URLs
- redirect URLs: `https://<origin>/sso-callback`
- sign-in and sign-up: `/sign-in`
- Google OAuth enabled if the custom sign-in flow offers Continue with Google

This web-layer Clerk gate does not replace Convex identity. Persistence remains an anonymous session seam unless a later change maps Clerk users into Convex.

Never place secrets in a `VITE_*` variable. The anonymous Convex session demonstrates isolation, not production authentication or tenant security.

## 3. Link and audit Vercel

**External action — approval required.** From the repository root:

```bash
bunx vercel@latest link
bunx vercel@latest env ls preview
bunx vercel@latest env ls production
```

Add or update each public value explicitly for Preview and Production as appropriate:

```bash
bunx vercel@latest env add VITE_CONVEX_URL preview
bunx vercel@latest env add VITE_DOCS_URL preview
bunx vercel@latest env add VITE_SITE_URL preview
bunx vercel@latest env add VITE_CLERK_PUBLISHABLE_KEY preview
bunx vercel@latest env add CLERK_SECRET_KEY preview
```

Repeat for `production` only after the production values are known. Do not copy a development Convex URL or Clerk test keys into Production and do not infer a domain or account from local state.

## 4. Deploy a Preview

**External action — approval required.** Create a non-production deployment and capture its immutable URL:

```bash
DEPLOYMENT_URL="$(bunx vercel@latest deploy)"
bunx vercel@latest inspect "$DEPLOYMENT_URL" --wait --timeout=10m
```

If deployment protection is enabled, use `vercel curl` or the authorized browser session; do not disable protection merely for the smoke test.

## 5. Preview smoke test

Test the immutable Preview URL, not only a branch alias:

1. Load `/` and confirm the landing page renders in Geist Mono with no console or server errors.
2. Load `/playground` at desktop and mobile widths.
3. Confirm the playground is labelled `Local-only` and exposes no cloud-persistence controls.
4. Load the sample template and compile it in the browser worker.
5. Confirm the engine-owned template preview, manifest, generated schema, and starter data appear.
6. Render the sample and confirm upright, searchable PDF text and the expected page count.
7. Download the PDF and validate that the downloaded bytes begin with `%PDF-` and open successfully.
8. Upload the migrated K3 compatibility template when it is available locally and confirm an upright four-page render with zero diagnostics.
9. Confirm no document or data requests leave the browser during compilation and rendering.
10. Inspect deployment and runtime logs for uncaught errors:

```bash
bunx vercel@latest inspect "$DEPLOYMENT_URL" --logs
bunx vercel@latest logs "$DEPLOYMENT_URL"
```

A passing Preview proves only that exact deployment and configured environment. Record the immutable deployment URL, commit SHA, Bun/Node versions, smoke timestamp, and any skipped step.

## 6. Stage and promote Production

**External action — separate approval required.** Build a production deployment without assigning domains, smoke its immutable URL, then promote that exact deployment:

```bash
PRODUCTION_CANDIDATE_URL="$(bunx vercel@latest deploy --prod --skip-domain)"
bunx vercel@latest inspect "$PRODUCTION_CANDIDATE_URL" --wait --timeout=10m
bunx vercel@latest promote "$PRODUCTION_CANDIDATE_URL"
```

Repeat the smoke test against the canonical production origin after promotion. Do not treat a successful Preview as production proof.

## 7. Rollback

If the post-promotion smoke fails, stop writes where possible, preserve the failed deployment URL and logs, then roll back to the last known-good production deployment:

```bash
bunx vercel@latest rollback
bunx vercel@latest rollback status
```

Re-run the landing-page, local-only playground, download, and no-external-request smoke against the restored production domain. A rollback restores an earlier deployment configuration; separately audit any environment-variable changes made during the incident.

## 8. Mintlify deployment

The canonical docs source is `docs/`. Deploy it through the approved Mintlify project, record the resulting origin, set `VITE_DOCS_URL` for Preview and Production, and redeploy the web app. Until that origin is configured, `/docs` deliberately shows a configuration-required page rather than serving a second documentation implementation.

## Evidence record

For every release, retain:

- repository commit and clean/dirty state;
- `bun run ci` output;
- immutable Preview and production-candidate URLs;
- exact environment names and variable names, never secret values;
- smoke results and screenshots at desktop/mobile widths;
- Vercel build/runtime log review;
- promoted deployment ID or rollback target;
- Mintlify origin and docs validation result;
- npm package versions and registry integrity only if publication was separately approved.
