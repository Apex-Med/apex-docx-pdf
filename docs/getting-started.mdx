# Getting started

Use a standard DOCX main document containing paragraphs and text runs. Put an inline value tag such as `{{customer.name}}` in its text, then compile once and render with data.

## 1. Prepare a template

In Word or another DOCX editor, add a paragraph such as:

```text
Hello, {{customer.name:string}}
```

Save it as `letter.docx`. Phase 1 recognizes the logical text of a paragraph, so a value tag may span DOCX runs; authoring it in one run is still easier to inspect.

## 2. Compile and render

The engine requires an explicit `locale` and `timeZone` for every render.

```ts
import { createDocxPdfEngine } from "@apex-docx-pdf/engine"

const engine = await createDocxPdfEngine()
const templateBytes = new Uint8Array(await Bun.file("letter.docx").arrayBuffer())

const compiled = await engine.compile(templateBytes, {
  unsupportedFeatures: "strict",
})

const result = await engine.render(
  compiled,
  { customer: { name: "Apex" } },
  {
    locale: "en-ZA",
    timeZone: "Africa/Johannesburg",
    metadata: { title: "Example letter" },
    includeLayoutTrace: true,
  }
)

await Bun.write("letter.pdf", result.pdf)
```

`compiled` exposes a field manifest, a JSON Schema, starter data, and diagnostics. `result` contains PDF bytes, page count, a deterministic document hash, timings, diagnostics, and—when requested—a layout trace.

<Note>
The `Bun.file` and `Bun.write` lines are Bun conveniences. The engine itself accepts and returns `Uint8Array`, so an application can supply bytes from any supported runtime.
</Note>

## 3. Treat diagnostics as output

Compilation and rendering preserve diagnostics rather than hiding lossy behavior. A diagnostic has a stable code, severity, message, and, where available, DOCX source location and node ID. Do not treat a warning as proof that visual fidelity has been preserved; check [supported features](/supported-features).
