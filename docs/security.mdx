Treat DOCX, ZIP, XML, template text, JSON data, caller-supplied font bytes, and embedded raster bytes as hostile. The renderer diagnoses unsupported input, never evaluates template code, and never fetches template or image resources.

## Current default limits

| Limit                                 |                        Default |
| ------------------------------------- | -----------------------------: |
| Template bytes                        |                     20,000,000 |
| ZIP archive entries                   |                          2,000 |
| Decompressed bytes                    |                    100,000,000 |
| XML depth / nodes / text bytes        |   128 / 1,000,000 / 50,000,000 |
| Image parts / total image bytes       |               100 / 20,000,000 |
| Image side / pixels per image         |          100,000 / 100,000,000 |
| Image chunks / decoded working bytes  |           10,000 / 400,000,000 |
| Expression / object-traversal depth   |                        32 / 32 |
| JSON nodes / text bytes / array items | 100,000 / 10,000,000 / 100,000 |
| Loop iterations                       |                         10,000 |
| Expanded nodes / text bytes           |           100,000 / 10,000,000 |
| Pages                                 |                            500 |

JSON node/text, loop, expanded-node, and expanded-text limits are cumulative across one render. Each JSON array has its own item bound; expression and traversal depth are bounded separately. Nested blocks do not receive fresh expansion budgets. Every `each` item must be a plain object-shaped JSON value; arrays, primitives, accessors, sparse arrays, cycles, non-finite numbers, and other non-JSON inputs are rejected by the engine boundary.

The DOCX reader rejects unsafe ZIP paths, duplicate parts, ZIP64/multi-volume archives, malformed XML, forbidden `DOCTYPE`/entity declarations, invalid relationship roots, and external relationships. Before WordprocessingML parsing, a fail-closed package-security pass rejects macros/VBA, OLE embeddings, ActiveX controls, attached packages or executables, attached templates/toolbars, custom UI, web extensions/task panes, and alternative-format chunks. Detection uses conventional package paths plus structured content-type and relationship-type declarations, so an orphan active part or a renamed relationship target cannot bypass the boundary. These security errors are unconditional and are never downgraded by compatibility mode. The package root must contain exactly one internal `officeDocument` relationship. The numbering part must be reached through the main document's internal numbering relationship; invalid or ambiguous numbering references are diagnosed.

Table parsing rejects missing/empty/non-positive grids, unsafe width sums, uncovered or overlapping rows, spans beyond the grid, inconsistent explicit widths, invalid merge chains, non-contiguous header declarations, and unsupported table properties. Percentage widths, nested tables, table styles/themes, complex shading, and complete Word autofit are rejected rather than interpreted heuristically. Static images may appear in supported table-cell paragraphs, subject to both table and image limits. A `cantSplit` row taller than a fresh writable page is fragmented deterministically with a warning so rendering cannot stall; page and expansion limits still apply to multi-page and repeated-row output.

Static image relationships must be internal and owner-relative. Every static placement requires one inline drawing, an internal PNG/JPEG part, and an explicit positive extent. A canonical dynamic `{{@image path}}` value instead requires caller-owned PNG/JPEG bytes, positive pixel dimensions, and positive physical twip bounds before layout; URLs are never resolved. The parser and image-preparation path check declared MIME against signature and dimensions, limit total distinct resources/bytes and each image's side/pixel area, and reject external relationships, anchors, malformed drawings, locked-aspect mismatches, APNG, interlaced or invalid-profile PNG, invalid chunk order/CRC/filter/scanline sizes, unsupported JPEG frames/scans/orientation/color transforms, ICC profiles, CMYK/YCCK, and ambiguous color. Preparation repeats bounded structural checks before allocation, normalizes supported PNG data to 8-bit gray/RGB plus optional alpha, and retains JPEG bytes only inside the bounded accepted profile. Crop, rotation, SVG, and network image acquisition remain unsupported.

Image preparation accepts `AbortSignal` and checks it throughout hashing, chunk/marker parsing, row/sample processing, and around decompression. PNG inflate uses a bounded caller-owned output buffer, but the underlying inflate call is synchronous: cancellation cannot interrupt it mid-inflate and is observed immediately before or after that call.

Only deterministic `nextPage` sections are accepted. Page geometry must use positive integer twips and agree with portrait/landscape orientation. Default and first-page header/footer relationships must be internal; references inherit across sections until replaced, and `w:titlePg` activates the first-page variants. Distances must be non-negative and header/footer content may not collide with body margins. Even-page header variants, continuous/odd/even breaks, automatic numbering in headers/footers, and non-decimal/arbitrary fields are rejected. `PAGE`/`NUMPAGES` reserve bounded width before pagination and materialize only after the global page count is known.

Template paths cannot address prototype-related fields, inherited properties are not traversed, and values are resolved without executing code. The safe formatter set is closed. Currency and date formatting accept only the engine-owned canonical `en-US` and `en-ZA` profiles; date formatting additionally requires an explicit time zone and offset-bearing ISO date-time. No formatter reads ambient locale data, time zone, or clock state.

The low-level library font configuration accepts explicit `Uint8Array` programs only. The adapter performs no filesystem access, system-font discovery, network fetch, or `Buffer`-specific processing. Font licensing and redistribution rights remain the caller's responsibility.

The reference playground is stricter: it does not register uploaded DOCX embedded-font programs. It resolves only six application-owned, hash-pinned OFL TrueType families shipped with the app. System-family names are aliases to catalog faces rather than OS lookups, and unavailable families stay visible in diagnostics. This keeps uploaded font programs outside the browser rendering trust boundary and prevents output from varying with the host machine.

## Application responsibilities

- Apply tenant authorization before reading template bytes, creating download URLs, or storing output.
- Enforce upload/rate policies in addition to engine limits.
- Keep large DOCX and PDF artifacts in file storage rather than database documents or web-server request bodies.
- Keep document text, DOCX/PDF bytes, render JSON, and bearer storage URLs out of logs. Persist only bounded, redacted diagnostics and operational metadata appropriate to the data policy.
- Use `AbortSignal` to stop abandoned work.
- Do not add network fetches, system-font lookup, executable helpers, or ambient locale/time/clock dependencies inside rendering stages.
- Preserve source-located image, section, field, header/footer, and table diagnostics; review warnings such as oversized `cantSplit` rows or table headers too tall to repeat. Do not equate a produced PDF with full Word fidelity.
- Treat dynamic/external/floating/cropped/rotated/SVG images, unsupported image profiles/colors, percentage/nested/styled/themed tables, non-`nextPage` sections, even-page headers, and header/footer numbering as unavailable until later phases establish explicit boundaries.

## Convex reference boundary

The Phase 7 reference adapter uses an anonymous per-browser session identifier from `convex-helpers`. It scopes records for the demo, but it is not authentication: it does not prove a person's identity, organization, role, or entitlement. Production hosts should replace the principal-establishment seam with verified Clerk or WorkOS identity while preserving the session-owned data access contract and its server-side ownership checks.

Persistence is opt-in and off by default. When it is disabled, the browser renderer must not invoke persistence uploads or save render artifacts. When it is enabled, the browser uploads DOCX bytes directly to a Convex generated upload URL; large document bytes must not be proxied through or buffered by a Vercel server function. Large DOCX and PDF artifacts remain in file storage, with storage IDs and bounded metadata stored in application records.

Before an uploaded storage ID can be consumed, a session-bound Convex registration action reads the immutable blob and verifies bounded content. PDFs must begin exactly with `%PDF-`. DOCX files must be classic single-volume ZIP packages with bounded entry and declared-decompression counts, a bounded central directory, safe unique paths, supported compression methods, and the required content-types, root-relationships, and main-document parts. This server-side gate rejects mislabeled arbitrary bytes, malformed or incomplete ZIPs, encrypted entries, and oversized packages; it does not inflate and semantically re-parse OOXML or replace the browser engine's stricter active-content and relationship checks. Convex may materialize more of a storage blob than the bounded slices requested by the action. Production malware scanning and quarantine remain host responsibilities.

Every file read begins with an ownership check. A bearer URL is generated only after that check and must not be treated as fine-grained authorization, a durable identifier, or safe log data. The underlying storage ID, not the generated URL, belongs in the database.

Saved render reuse is session-owned and keyed by the exact `engineVersion`, `templateHash`, `fontRegistryHash`, `dataHash`, and `renderOptionsHash`. Results never cross an engine-version boundary. Status queries must use ownership-scoped indexes and cursor pagination; realtime subscriptions observe those bounded records rather than authorizing them.

Deletion removes both the template storage object and saved PDF storage objects through bounded, resumable cleanup. Direct uploads use 65-minute session-owned intents, five minutes longer than Convex's documented generated-URL lifetime. The server returns an intent-specific MIME marker that the browser must use for its POST, consumers bind the resulting storage ID exactly once, and scheduled cleanup searches that intent's bounded storage creation-time window for the marker. This lets the normal app path reclaim an upload even if the tab closes after the storage POST but before registration. Registered-but-unconsumed files are also deleted; consumed files remain protected until their owning template or render is deleted. A client that deliberately ignores the returned marker is outside this adapter's reclamation guarantee, so deployment-level storage audits remain prudent.

See [Convex integration](/convex) for the complete storage, cache, lifecycle, and local-versus-production contract.
