# Package size review

Date: 2026-08-05. Measurements are generated by `bun scripts/review-package-size.ts` from current local source and `apps/web/dist` artifacts. See `package-size-measurements.json` for exact raw and per-file gzip byte counts.

The package export maps currently point at TypeScript source, so there are no package-level distribution bundles to measure. Source byte totals are useful for relative ownership only; they are not install size or transferred JavaScript. The existing web build is included because it is the only local bundled artifact available.

Measured snapshot:

- Package source: 560,441 raw bytes across 55 TypeScript/TSX files; 135,830 bytes using per-file gzip.
- Existing web distribution: 8,432,585 raw bytes across 46 files; 3,060,150 bytes using per-file gzip.
- Largest JavaScript artifact: playground chunk, 1,673,942 raw / 499,704 gzip bytes.
- Browser engine worker: 708,746 raw / 123,612 gzip bytes.
- Render worker: 619,360 raw / 233,988 gzip bytes.
- Largest package source areas: DOCX 174,631 raw bytes, layout 97,687, and template 62,979.

Key review points:

- Keep engine consumers on the facade so bundlers do not need application code or testkit.
- The browser worker is expected to carry most of the document pipeline. Track its emitted asset separately from the playground route, which includes viewer/editor dependencies.
- Font files and the DOCX WASM asset are content assets and must not be compared directly with JavaScript gzip totals.
- Per-file gzip totals intentionally do not establish a regression threshold. Gather comparable clean-build measurements in CI before choosing budgets.
- A future publishable build should report raw, gzip, and sourcemap-excluded sizes for each public entry/subpath, plus a minimal consumer bundle. Current source exports cannot provide that evidence.

This report does not claim npm package, Node, browser runtime, or Vercel deployment size proof.
